# Phase 1: Cart schema and mappings

## Overview

V9 creates `carts` and `cart_items` with the project's conventions. This phase adds the `cart/` feature's entities,
repositories and properties, plus the test fixtures phases 2–3 need. No endpoint yet. `ddl-auto: validate` passing
at startup is this phase's check.

## Context

- `spring-base/CLAUDE.md`:
  - "Decided (2026-10-21)": bigint identity ids, `version`, auditing, `varchar(3)` + regex for `char(3)`, and a
    FK to a missing table is added by the migration that creates it, so `currency` gets no FK until `currencies`
    exists
  - Conventions: `BaseEntity`, `@NoArgsConstructor(access = PROTECTED)`, a static `create(...)`, no
    `@Data`/`@ToString`
  - Persistence: the repositories pattern (`XRepository` + `XRepositoryCustom` + `impl/XRepositoryImpl`, no
    `@Query`)
- `DATABASE-SCHEMA.md` `carts`, `cart_items` (the user's 13 Nov edit)
- `db/migration/V2__create_product_tables.sql` (standard columns), `V7__create_wishlist_table.sql` (header comment
  style)
- Lock pattern: `auth/repository/impl/UserSessionRepositoryImpl.findByTokenHashForUpdate`
- Properties pattern: `search/config/SearchProperties`, `destination/sync/DestinationSyncProperties`
- Tests: `support/CatalogFixtures` (`roomType` adds a default rate plan; `ratePlan(...)` builder)

## Requirements

- Functional:
  - one cart per user
  - lines keyed by (cart, rate plan, check-in, check-out, adults, child ages)
  - the stored per-room price for the notice
- Non-functional:
  - the schema enforces the line rules (dates, quantity ≥ 1, adults ≥ 1, `children = cardinality(child_ages)`)
  - the expiry delete is indexed

## Architecture

```sql
-- V9__create_cart_tables.sql
-- Each signed-in customer's cart (C-CART-01..04). Guests keep their cart in the browser and merge it on sign-in, so
-- unlike the original schema there is no guest_token and user_id is required. Table and column names follow
-- DATABASE-SCHEMA.md; ids, version and timestamps follow this project.
create table carts (
    id         bigint generated by default as identity primary key,
    user_id    bigint      not null unique references users (id) on delete cascade,
    version    bigint      not null default 0,
    created_at timestamptz not null,
    updated_at timestamptz not null
);

-- A cart holds lines of any hotel and dates; the hotel comes from the rate plan. Lines of one hotel with the same
-- check_in and check_out are checked out together as one booking.
create table cart_items (
    id                 bigint generated by default as identity primary key,
    cart_id            bigint      not null references carts (id) on delete cascade,
    rate_plan_id       bigint      not null references rate_plans (id) on delete cascade,
    check_in           date        not null,
    check_out          date        not null,
    quantity           smallint    not null default 1 check (quantity >= 1),
    adults             smallint    not null check (adults >= 1),          -- per room
    children           smallint    not null default 0 check (children >= 0),
    child_ages         smallint[]  not null default '{}',                 -- per room, sorted
    price_at_add_minor bigint      not null check (price_at_add_minor >= 0), -- one room, whole stay; notice only
    currency           varchar(3)  not null check (currency ~ '^[A-Z]{3}$'),
    version            bigint      not null default 0,
    created_at         timestamptz not null,
    updated_at         timestamptz not null,
    check (check_out > check_in),
    check (cardinality(child_ages) = children),
    check (0 <= all (child_ages) and 17 >= all (child_ages))
);

-- One line per rate, stay and guests; also serves lookups by cart (replaces the doc's cart_items_cart_id_idx).
create unique index cart_items_line_key on cart_items (cart_id, rate_plan_id, check_in, check_out, adults, child_ages);
-- The expiry job deletes by check-in.
create index cart_items_check_in_idx on cart_items (check_in);
```

`findLines` joins `i.ratePlan rp join rp.roomType rt join rt.hotel h`. It doesn't filter by status, so a line whose
plan, room type or hotel stopped selling is still read and then marked `UNAVAILABLE`.

## Implementation Steps

1. Write V9 as above. Copy the standard columns from V2.
2. `Cart`: `@Table(name = "carts")`, `@Column(name = "user_id", nullable = false, updatable = false) Long userId`,
   `static Cart create(long userId)`.
3. `CartItem`:
   - `childAges` maps the `smallint[]` column as `Short[]` (Hibernate 7 basic array).
   - The getter returns `List<Integer>`, and `create` stores the ages sorted, with `children = ages.size()`.
   - `create`, `changeQuantity`, `changeStay` and `rebasePrice` hold the field rules.
   - Equality is inherited from `BaseEntity`.
4. Repositories as listed:
   - `findByUserIdForUpdate`: JPQL `select c from Cart c where c.userId = :userId` + `PESSIMISTIC_WRITE`
   - `findLines`: `select new ...CartLineView(...)`
   - `deleteCheckedInBefore`: `delete from CartItem i where i.checkIn < :day`, returning the count
   - `RatePlanRepositoryImpl.findSeller`: a JPQL `select new`, with no status filter (the room list query decides
     what is sellable)
5. `CartProperties` record, `@Validated`. It is picked up by `@ConfigurationPropertiesScan`.
6. Fixture helpers, then `CartItemRepositoryTest`:
   - `findLines` returns the line with sorted ages and the hotel's currency
   - the unique index rejects a second equal line
   - `deleteCheckedInBefore` removes only earlier check-ins
   - `findByUserIdForUpdate` finds the cart
7. Run `./mvnw test -Dtest=CartItemRepositoryTest`, then start the app once (`./mvnw spring-boot:run`) to see Flyway
   apply V9 and `validate` pass.

## Risk Assessment

- **`smallint[]` ↔ `Short[]` validation**: no entity maps an array yet.
  - Fallback 1: `@JdbcTypeCode(SqlTypes.ARRAY)` with `columnDefinition = "smallint[]"`.
  - Fallback 2: a `List<Short>` with the same annotation.
  - Last resort: `int[]` plus `integer[]` in V9 (a schema-doc deviation, to note in phase 4).
- **Array equality in the unique index**: it holds only if ages are always stored sorted. That is the entity's job,
  not the caller's.
- **`deleteByIdAndCartUserId` derived delete**: Spring Data loads, then deletes. That's fine for one row, and it
  needs `@Transactional` on the caller.
- Rollback: delete V9 before it runs anywhere shared. Locally, follow `plan.md` Rollback.
