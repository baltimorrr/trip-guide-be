# Phase 4: Sample product feature and README

## Overview

Add one complete reference feature (`product` CRUD) that shows the template's conventions end to end: migration → entity → repository → service → controller → DTOs → tests, plus role checks and pagination. Then write the README and run the final verification.

Context: [phase 3](./phase-03-jwt-authentication-and-authorization.md), [plan acceptance criteria](./plan.md)

## Key Insights

- Return `PagedModel<T>` (Spring Data) instead of a raw `Page<T>`. `Page`'s JSON shape is not stable across versions, and Spring Data warns when it is serialized directly. `PagedModel` gives `{content: [...], page: {size, number, totalElements, totalPages}}`.
- Use `@PreAuthorize` on controller methods. It is the most visible place for a learner to see who can call what, and it exercises the 403 path from phase 3.
- Clients don't send `version`, so `@Version` only protects against concurrent transactions, not stale client edits. That's enough for a template; the README notes it.

## Requirements

- Functional:
  - `GET /api/products?page&size&sort` → 200 paged (any authenticated user). `size` capped at 100
  - `GET /api/products/{id}` → 200, or 404 ProblemDetail
  - `POST /api/products` (ADMIN) → 201 + `Location: /api/products/{id}`
  - `PUT /api/products/{id}` (ADMIN) → 200 / 404
  - `DELETE /api/products/{id}` (ADMIN) → 204 / 404
  - USER calling a write → 403 ProblemDetail; no token → 401
- Non-functional: README lets someone with only JDK 21 + Docker run the app and tests in under 10 minutes

## Architecture

```text
product/
├── Product.java            entity: name, description, price (BigDecimal 12,2)
├── ProductRepository.java  JpaRepository<Product, Long>
├── ProductService.java     @Transactional(readOnly = true) class-level; writes @Transactional
├── ProductController.java  /api/products, @PreAuthorize on writes
└── dto/ProductRequest.java, dto/ProductResponse.java (records)
```

## Implementation Steps

1. Migration `V2__create_products.sql`:
   ```sql
   create table products (
       id          bigint generated by default as identity primary key,
       name        varchar(120)   not null,
       description varchar(1000),
       price       numeric(12, 2) not null check (price >= 0),
       version     bigint         not null default 0,
       created_at  timestamptz    not null,
       updated_at  timestamptz    not null
   );
   ```
2. `Product` extends `BaseEntity`. Lombok `@Getter @Setter @NoArgsConstructor(access = PROTECTED)`. Add an `update(name, description, price)` method so the service never sets fields one by one.
3. DTOs:
   - `ProductRequest(@NotBlank @Size(max=120) name, @Size(max=1000) description, @NotNull @DecimalMin("0.00") @Digits(integer=10, fraction=2) BigDecimal price)`
   - `ProductResponse(id, name, description, price, createdAt, updatedAt)` + `static from(Product)`
4. `ProductService`: `findAll(Pageable)` → `Page<ProductResponse>`; `findById` → `ResourceNotFoundException("Product", id)`; `create`; `update`; `delete` (404 if missing). Use `saveAndFlush` on create so `createdAt`/`version` appear in the response.
5. `ProductController`:
   ```java
   @GetMapping
   PagedModel<ProductResponse> list(@PageableDefault(size = 20, sort = "id") Pageable pageable) {
       return new PagedModel<>(service.findAll(pageable));
   }
   @PostMapping @PreAuthorize("hasRole('ADMIN')")
   ResponseEntity<ProductResponse> create(@Valid @RequestBody ProductRequest req) {
       ProductResponse created = service.create(req);
       return ResponseEntity.created(URI.create("/api/products/" + created.id())).body(created);
   }
   // get / put / delete similarly; delete returns ResponseEntity.noContent().build()
   ```
6. `application.yml`: `spring.data.web.pageable.max-page-size: 100`.
7. `support/TestAuth`: static helpers `registerAndLogin(MockMvcTester)` → user token, and `adminToken(MockMvcTester)` → logs in with the bootstrap admin from `application-test.yml`.
8. `ProductApiTests` (`@IntegrationTest`):
   - no token GET → 401; USER GET list → 200 with `content` + `page.totalElements`
   - USER POST/PUT/DELETE → 403 problem+json (proves the catch-all doesn't swallow `AccessDeniedException`)
   - ADMIN POST → 201 + `Location`; GET by id → 200; PUT → 200 with updated fields; DELETE → 204, then GET → 404 problem+json
   - invalid body (blank name, `price: -1`, `price: 1.234`) → 400 with `errors[]` naming each field
   - `?sort=nope` → 400 (not 500); `?size=1000` → `page.size` == 100
9. `README.md` sections:
   - What this is
   - Stack + versions (table from the research report)
   - Prerequisites (JDK 21, Docker)
   - Quick start:
     ```bash
     cp .env.example .env
     openssl rand -base64 32     # paste into APP_JWT_SECRET
     ./mvnw spring-boot:run      # run from project root
     ```
   - curl walkthrough (register → login → `export TOKEN=…` → products)
   - Swagger URL
   - Tests (`./mvnw verify`, needs Docker)
   - Project structure
   - **"Adding a feature" checklist**: `V{n}__*.sql` → entity extends `BaseEntity` → repository → service → DTO records → controller + `@PreAuthorize` → `@IntegrationTest` tests
   - Conventions: package-by-feature; no `@Data` on entities; DTOs are records; never edit an applied migration
   - Configuration/env var table
   - Production notes (`SPRING_PROFILES_ACTIVE=prod`, `SPRING_DATASOURCE_URL/USERNAME/PASSWORD`, `./mvnw spring-boot:build-image`, Swagger off in prod)
   - Using as a template (copy the folder, rename `groupId`/`artifactId`/package, `git init`)
   - Known limitations: no refresh/revocation, no rate limiting, 409 reveals registered emails, `@Version` not client-exposed
10. Final verification (Success Criteria) + `git status` review. Commit only if the user asks.

## Risk Assessment

| Risk | Mitigation |
|------|------------|
| `PagedModel` JSON shape differs from the expectation | the test asserts the exact field paths; adjust the README example to the real output |
| Invalid sort → 500 | phase 2 `PropertyReferenceException` handler + test here |
| Tests flaky from shared DB state | unique data per test; assert on created ids, not total counts |
| README drift | the fresh-clone simulation step is mandatory |

## Security Considerations

- Writes ADMIN-only via `@PreAuthorize`; reads require authentication
- 404 vs 403 ordering: a USER deleting a missing id gets 403 (authorization runs before lookup), which avoids revealing which ids exist
